# sigmensa 멀티 에이전트 오케스트레이션

이 워크스페이스의 `.claude/agents/`에 정의된 에이전트들을 조합하는 기준.
메인 세션(오케스트레이터)은 직접 대량 구현을 하지 않고, 작업을 분해해 에이전트에
위임하고 결과를 검증·종합한다.

## 에이전트 로스터 (7종)

| 에이전트 | 역할 | 쓰기 권한 | 통신(Agent/SendMessage) | 스킬 | 모델 |
|---|---|---|---|---|---|
| `orchestrator` | 중앙 지휘(분해·위임·종합) | X (코드 금지) | **O — 유일** | 전체 | inherit |
| `dev` | 구현(전 스택, 1회 실행 = 1레포) | O | X | 해당 레포 run/verify만 | inherit |
| `qc` | 검수(버그/회귀/계약) | X (읽기 전용) | X | `*:verify`만 | **opus** |
| `quality` | 무동작변경 개선(코드량+성능) | O | X | 없음 | sonnet |
| `test-writer` | 테스트 추가 | O (테스트 위주) | X | 없음 | sonnet |
| `design` | 디자인 검수/교정(frontend) | O | X | 없음 | sonnet |
| `scribe` | API 문서 최신화 + 알기쉬운 주석 | O (문서·주석만) | X | 없음 | sonnet |

역할 경계: 기능을 바꾸면 `dev`, 바꾸지 않고 개선하면 `quality`, 판단만 하면 `qc`,
문서·주석은 `scribe`, 여러 에이전트를 지휘해야 하면 `orchestrator`.

## 통신·스킬 정책

- **통신은 오케스트레이터 단일 창구**: `Agent`(에이전트 생성)와 `SendMessage`는
  orchestrator만 보유한다. 워커끼리 직접 통신 금지 — 계약/변경사항은 반드시
  오케스트레이터를 경유해 전달한다(정보 누락·모순 전파 방지).
- **스킬은 한정 부여**: dev는 자기 레포의 run/verify 스킬만, qc는 verify 스킬만,
  나머지 워커는 스킬 없음. `/harness` 같은 오케스트레이션 스킬은 orchestrator 전용.
- API가 바뀐 기능 라운드는 **scribe 후속 투입이 기본**(문서·주석 최신화가 마지막 단계).

## 모델 선택 기준 — 오케스트레이터가 가장 위

- **오케스트레이터(메인 세션) ≥ 모든 에이전트**: 가장 비싼 실수는 에이전트의 코드
  실수가 아니라 오케스트레이터의 분해 실수다(잘못된 계약 전달, 순서 뒤바꿈, 컨텍스트
  누락 → 전 라운드 재작업). 메인 세션은 가능한 최상위 모델로 돌리고, 에이전트는
  아래 기준으로 낮춘다. 절감이 필요하면 에이전트부터 낮추고 오케스트레이터는 마지막에.
- **qc = opus**: 마지막 방어선 + 산출물이 보고뿐이라 토큰량이 작다 — 추론 품질 투자
  대비 효율 최고 지점. 읽기 전용이라 강한 모델이 코드를 건드릴 위험도 없다.
- **dev = inherit**: 구현 품질은 세션 수준을 따라가게 한다. 세션 하나만 조절하면
  전체 파이프라인 비용/품질이 함께 움직인다(이중 설정 방지).
- **quality/test-writer/design/scribe = sonnet 고정**: 기존 컨벤션 모방 비중이 커서 sonnet이
  최적. 세션이 opus여도 과소비 방지, 세션이 낮아져도 품질 하한 유지.
- **haiku 슬롯 없음**: 단순 탐색은 내장 Explore가 커버. 이 로스터는 전부 판단 작업.
- **도구 제한**: qc·orchestrator는 Edit/Write 제외(검수는 수정 금지, 지휘는 실행
  분리의 기계적 강제). 전원 Bash/PowerShell 보유(검증 명령 필수). 에이전트 생성·통신은
  orchestrator 단독 — 워커의 재귀 호출 금지.

## 표준 파이프라인

### 1. 기능 구현 (계약 우선)
```
dev@backend (스키마+API, 계약 확정)
  → dev@frontend (확정된 계약으로 UI)   ← 계약 JSON을 프롬프트에 그대로 전달
  → qc (양쪽 diff 교차 검수)
  → test-writer (새 분기 커버)
```
백엔드와 프론트를 동시에 띄우지 않는다 — 계약이 확정되기 전에 프론트를 만들면
필드명 불일치가 난다. 반드시 dev@backend의 보고에서 계약을 받아 dev@frontend에 넘긴다.

### 2. 독립 작업 병렬화
서로 다른 레포(frontend/backend/agent)를 건드리는 독립 작업은 **한 메시지에서 동시에**
에이전트를 띄운다. 같은 레포의 같은 파일을 두 에이전트가 만질 가능성이 있으면 순차로.

### 3. 품질 라운드 (기능 안정 후)
```
quality (레포별 병렬, 코드량+성능 한 번에)  →  qc  →  test-writer
```
같은 레포에 쓰기 에이전트 2개를 동시에 띄우지 않는다(충돌).

### 4. 검수 단독
배포 전/커밋 전에는 `qc`만 단독으로: diff 범위 확정 → 스택별 검증 명령 실행 →
심각도별 보고. 치명/버그가 있으면 해당 스택 dev 에이전트에 수정을 위임하고 qc 재실행.

## 속도 규칙 (지연의 실측 원인 기반)

- **소규모 수정은 위임하지 않는다**: 파일 1~2개·수십 줄 이하의 수정은 오케스트레이터/
  메인 세션이 직접 한다. 워커 위임은 콜드 스타트 세금(문서 재독+코드 재탐색 3~5분)이
  붙으므로, 탐색이 필요하거나 파일이 여러 개일 때만.
- **Gradle 데몬**: compile/test 검증은 데몬 사용(`--no-daemon` 금지 규칙은 bootRun
  전용). 워커에게 이 예외를 프롬프트에 명시.
- **테스트 선별 실행**: 작업 중엔 영향 패키지만 `--tests` 필터로, 전체 스위트는
  커밋 직전 qc 라운드에서 1회.
- **HARNESS.md는 섹션 지정**: 워커 프롬프트에 "HARNESS.md의 X 섹션만 읽어라"로
  지목한다. 파일 전체 읽기 금지.
- **위임 배치화**: 같은 레포에 순차로 들어갈 작은 작업 여러 개는 하나의 워커
  프롬프트로 묶는다(콜드 스타트 1회로 처리).

## 오케스트레이터 규칙

- **프롬프트에 컨텍스트를 다 담는다.** 에이전트는 이 대화를 못 본다. 파일 경로,
  확정된 계약, 이전 라운드에서 밝혀진 함정(예: SchemaInitializer가 기존 테이블을 못
  고치는 문제, `.env` 테스트 누수)을 프롬프트에 명시.
- **HARNESS.md가 인수인계 문서다.** 각 레포의 `HARNESS.md`에 라운드별 결정과 이유가
  누적된다. 에이전트에게 "읽고 시작, 끝나면 append"를 지시한다. 설계가 뒤집히면
  해당 섹션을 교체(REPLACE)하게 해서 모순된 두 버전이 남지 않게 한다.
- **커밋은 오케스트레이터가.** 에이전트에게는 항상 "do not commit"을 지시하고,
  사용자 승인 후 레포별로 커밋·푸시한다.
- **실패한 에이전트는 결과를 확인하고 재실행.** 짧은 시간에 죽었거나(토큰 수 이상)
  메타 발언만 반환한 경우 작업이 수행되지 않은 것 — `git status`로 실제 변경 여부를
  확인한 뒤 동일 프롬프트로 재실행한다.
- **루트 AGENTS.md 우선.** 백그라운드 기동 금지, 포트 정리 절차, 로그 위치 등
  워크스페이스 공통 규칙은 모든 에이전트에 적용된다.
