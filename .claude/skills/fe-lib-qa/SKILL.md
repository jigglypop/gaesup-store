# FE Lib QA — 라이브러리 경계면 교차 검증

각 파트가 개별적으로 "올바르게" 만들어져도 연결 지점에서 계약이 어긋나는 것이 라이브러리 결함의 주요 원인이다. 이 스킬의 모든 검증은 **존재 확인이 아닌 교차 비교**다 — 반드시 경계 양쪽을 동시에 열어 비교한다.

## 검증 시점

- **점진 검증**: 모듈 완료 알림마다 해당 모듈의 경계면 즉시 검증 (결함 전파 차단)
- **최종 검증**: 전체 완성 후 아래 체크리스트 전량 수행

## 경계면 체크리스트

각 항목은 (왼쪽: 생산자) ↔ (오른쪽: 소비자)를 동시에 읽는다.

### 1. 계약 ↔ 구현
- [ ] 계약 Export 표의 모든 항목이 실제로 export됨 (누락 없음)
- [ ] 실제 export 중 계약에 없는 것이 없음 (무단 표면 확장 없음)
- [ ] 시그니처 일치 — 파라미터 수·타입·옵셔널 여부·반환 타입을 항목별 대조
- [ ] 계약의 에러 조건에서 실제로 명시된 에러가 throw됨

방법: 계약 문서의 Export 표와 진입점 파일을 나란히 놓고 표를 한 줄씩 대조. `Grep`으로 `export` 전량 추출 후 계약에 없는 이름을 역방향 확인.

### 2. 타입 ↔ 런타임
- [ ] 공개 경계에 `any` 없음 (`Grep`: 공개 모듈에서 `: any`, `as any`)
- [ ] 타입 캐스팅으로 우회된 지점이 런타임 shape과 일치 — 캐스팅 지점을 전부 찾아 실제 값의 출처를 추적
- [ ] `@ts-ignore`/`@ts-expect-error`가 공개 경로에 없음

### 3. package.json ↔ 빌드 산출물 ↔ 소스
- [ ] `exports` 맵의 모든 경로가 빌드 산출물에 실제 존재 (빌드 전이면 빌드 설정의 entry와 대조)
- [ ] `sideEffects` 선언과 실제 코드 일치 — `false` 선언 시 최상위 사이드이펙트가 정말 없는지 소스에서 확인
- [ ] `types` 필드가 실제 `.d.ts` 위치를 가리킴
- [ ] 코어 모듈이 peerDependencies의 프레임워크를 import하지 않음 (코어/바인딩 경계)

### 4. 문서·예시 ↔ 실제 API
- [ ] 계약의 사용 예시가 실제 export 이름·시그니처로 컴파일 가능
- [ ] README/문서의 코드 예시 속 import 경로와 심볼이 실제 존재
- [ ] `@deprecated` 표시된 API가 문서에서 권장 예시로 쓰이지 않음

### 5. 테스트 ↔ 계약
- [ ] 계약의 모든 export가 테스트 리포트의 커버 표에 존재
- [ ] 테스트가 공개 진입점에서 import함 (내부 파일 직접 import 없음)
- [ ] 계약의 에러 조건마다 대응 테스트 존재

### 6. SemVer 정합성
- [ ] 기존 공개 API에서 제거·시그니처 변경된 것이 있는지 git diff로 확인
- [ ] 있다면 breaking으로 보고되었는지 확인 — 커밋/구현 노트에 `!` 또는 breaking 명시

## 리포트 형식

`_workspace/fe-lib/04_fe-qa_verification.md`:

```markdown
# QA 검증 리포트
## 요약
통과 N / 실패 N / 미검증 N
## 실패 항목
| # | 경계면 | 파일:라인 | 문제 | 수정 방법 | 담당 |
## 미검증 항목
| # | 항목 | 사유 |
```

판정 불가(빌드 산출물 부재 등)는 실패가 아닌 **미검증**으로 분류하고 사유를 남긴다. 미검증을 통과에 합산하지 않는다. 실패 항목은 발견 즉시 담당 에이전트에게 SendMessage로 전달한다 — 리포트 완성까지 기다리면 결함이 후속 작업에 전파된다.
