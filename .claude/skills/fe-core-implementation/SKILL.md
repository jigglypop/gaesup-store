# FE Core Implementation — 라이브러리 코어 코드 원칙

라이브러리 코드는 앱 코드와 다르다. 호출자를 통제할 수 없고, 모든 공개 표면이 영구 계약이며, 번들 크기와 트리셰이킹이 사용자 경험을 직접 결정한다. 아래 원칙은 그 차이에서 나온다.

## 구현 절차

1. `_workspace/fe-lib/01_fe-architect_api-design.md`의 계약을 읽는다 — 계약 없이 구현을 시작하지 않는다
2. 모듈 하나를 완성할 때마다 타입 체크를 통과시키고, 완료를 알린다 (전체 완성까지 묵음 금지)
3. 구현 노트(`02_fe-core-builder_impl-notes.md`)에 export별 상태를 기록한다

## 코드 원칙

### 1. 사이드이펙트 없는 모듈
모듈의 최상위 레벨에서 실행되는 코드(전역 등록, 즉시 실행, DOM 접근)를 두지 않는다. 번들러는 `sideEffects: false`를 신뢰하고 미사용 모듈을 제거하는데, 최상위 사이드이펙트가 있으면 이 약속이 깨져 사용자 번들에서 코드가 조용히 사라지거나 반대로 전부 포함된다. 초기화가 필요하면 명시적 `createX()` / `init()` 함수로 제공한다.

### 2. 전역 상태 금지, 인스턴스 기반 설계
모듈 스코프의 mutable 상태는 같은 페이지에 라이브러리가 두 번 로드되거나(버전 중복) 테스트가 병렬 실행될 때 오염된다. 상태는 팩토리 함수가 만든 인스턴스에 담고, 싱글턴이 필요하면 사용자가 자기 앱에서 만들게 한다.

### 3. 런타임 의존성은 기본 0
의존성 하나는 사용자에게 번들 크기·보안 감사·버전 충돌을 전가한다. 추가하려면 구현 노트에 근거(직접 구현 대비 이득)를 기록하고 fe-architect의 동의를 받는다. 타입 전용 의존은 `devDependencies`, 프레임워크는 `peerDependencies`에 둔다.

### 4. 엄격한 타입, 공개 경계에 any 금지
공개 API의 파라미터·반환 타입에 `any`를 쓰면 사용자 코드의 타입 안전성이 그 지점에서 전파되며 무너진다. 표현 불가한 타입은 `unknown` + 타입 가드로 처리한다. 내부에서 캐스팅이 불가피하면 이유를 주석으로 남긴다.

### 5. 에러 계약
- 예상 가능한 실패(잘못된 입력)는 명확한 메시지로 즉시 throw — 어떤 인자가 왜 잘못됐는지, 사용자가 자기 코드에서 고칠 수 있는 수준으로 쓴다
- 에러를 삼키지 않는다(silent catch 금지) — 라이브러리가 삼킨 에러는 사용자가 디버깅할 수 없다
- 계약에 정의된 에러 타입/코드가 있으면 그대로 사용한다

### 6. 입력 불변
받은 객체·배열을 변경하지 않는다. 호출자는 자신의 데이터가 함수 호출로 변할 것을 예상하지 못한다. 변경이 필요하면 복사 후 반환한다.

### 7. 순수 코어 + 얇은 바인딩
프레임워크(React 등) 의존 코드와 순수 로직을 분리한다. 코어는 프레임워크 없이 테스트 가능해야 하고, 바인딩은 코어를 얇게 감싸기만 한다. 코어에 `import react`가 나타나면 경계 위반이다.

### 8. ESM 우선, 명시적 export
- named export만 사용한다 — default export는 트리셰이킹과 re-export에서 이름 불일치 문제를 만든다
- 배럴 파일(index.ts)은 공개 진입점에만 둔다 — 내부 모듈 간 배럴 경유 import는 순환 참조와 번들 비대를 만든다
- 내부 전용 심볼은 진입점에서 export하지 않는다

### 9. SemVer 인식
공개 API의 시그니처·동작 변경은 커밋 타입으로 표현한다: 추가는 `feat:`, 버그 수정은 `fix:`, 기존 계약을 깨면 `feat!:`. 이 저장소의 CONTRIBUTING.md 커밋 컨벤션과 동일하다. breaking을 인지하지 못한 채 배포하는 것이 라이브러리의 최악 사고이므로, 확신이 없으면 fe-architect에게 판정을 요청한다.

- [ ] 계약의 시그니처와 실제 export 시그니처 일치
- [ ] 최상위 사이드이펙트 없음
- [ ] 공개 경계에 `any` 없음
