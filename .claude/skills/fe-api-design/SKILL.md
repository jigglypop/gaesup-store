# FE API Design — 공개 API 표면 설계

라이브러리의 공개 API는 한 번 배포되면 사실상 영구 계약이다. 설계 단계의 10분이 배포 후의 major 버전 하나를 아낀다.

## 설계 절차

1. **기존 표면 조사** — 진입점(index/exports map)에서 현재 공개 export 전량을 나열한다. 신규 설계가 기존 이름·패턴과 충돌하지 않아야 한다
2. **사용 예시부터 작성** — 시그니처를 정하기 전에, 사용자가 쓰게 될 코드 3~5줄을 먼저 써본다. 예시가 어색하면 API가 어색한 것이다
3. **계약 문서 작성** — 아래 출력 형식대로 `_workspace/fe-lib/01_fe-architect_api-design.md`에 기록
4. **SemVer 판정** — 각 변경을 patch / minor / major로 분류하고 근거를 남긴다

## 설계 원칙

### 표면 최소화
"나중에 쓸지도 모르는" export를 미리 열지 않는다. 추가는 minor로 언제든 가능하지만 제거는 major다. 의심스러우면 비공개로 시작한다.

### 단순 기본값 + 옵션 객체
필수 인자는 위치 인자로, 나머지는 단일 옵션 객체로 받는다. 위치 인자가 3개를 넘으면 호출부에서 의미를 읽을 수 없고, 옵션 객체는 하위 호환 확장이 가능하다.

```ts
// 좋음: 필수 1개 + 옵션 객체
createStore(initial, { equals, onChange })
// 나쁨: 위치 인자 나열 — 확장할 때마다 breaking
createStore(initial, equals, onChange, debug)
```

### 직교성
한 가지 일을 하는 작은 API를 조합 가능하게 설계한다. 옵션 플래그로 동작이 갈라지는 만능 함수 하나보다, 조합되는 함수 둘이 낫다. 플래그 조합의 수만큼 테스트와 문서 부담이 지수적으로 는다.

### 네이밍 일관성
동사 규칙을 라이브러리 전체에서 통일한다 — 생성은 `create*`, 변환은 `to*`, 판정은 `is*`/`has*`, 구독은 `on*`(해제 함수 반환). 기존 코드베이스에 확립된 규칙이 있으면 그것이 우선한다.

### 에러 계약도 API다
어떤 입력에서 throw하는지, 에러 타입/코드가 무엇인지를 시그니처와 함께 정의한다. throw 조건의 변경도 breaking일 수 있다.

### 폐기(deprecation) 경로
export를 제거·개명할 때는 한 minor 버전 동안 `@deprecated` JSDoc + 대체 API 안내를 거친 뒤 다음 major에서 제거한다.

## 출력 형식

`_workspace/fe-lib/01_fe-architect_api-design.md`는 다음 구조를 따른다:

```markdown
# API 설계: {기능명}
## 변경 요약 (재호출 시 이번 변경점을 최상단에)
## 모듈 맵
{모듈 경계와 의존 방향. 코어/바인딩 분리 명시}
## Export 표
| Export | 종류 | 시그니처 | 모듈 | SemVer |
## 동작 계약
{export별 핵심 동작, 엣지 케이스, 에러 조건}
## 사용 예시
{대표 시나리오 2~3개, 실제 컴파일 가능한 코드}
## 미해결 질문
{모호했던 요구와 선택한 해석}
```

Export 표의 시그니처는 TypeScript 시그니처 전문을 쓴다 — 요약하면 빌더·테스터가 각자 다르게 해석한다.
