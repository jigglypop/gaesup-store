# FE Lib Testing — 라이브러리 테스트 작성

라이브러리 테스트의 목적은 "구현이 돌아간다"가 아니라 **"공개 계약이 지켜진다"**의 증명이다. 기대값의 출처는 항상 API 계약 문서다.

## 테스트 절차

1. `_workspace/fe-lib/01_fe-architect_api-design.md`의 동작 계약에서 테스트 케이스를 도출한다
2. 모듈 완료 알림을 받으면 해당 모듈만 즉시 테스트한다 (incremental — 전체 완성 대기 금지)
3. 실행 결과를 `_workspace/fe-lib/03_fe-test-engineer_test-report.md`에 기록한다

## 작성 원칙

### 공개 API를 통해서만 테스트
공개 진입점에서 import한다. 내부 파일 직접 import 테스트는 리팩토링마다 깨져서, 결국 "테스트가 무서워 리팩토링을 못 하는" 라이브러리를 만든다. 내부 로직은 공개 API의 입출력으로 간접 검증한다.

### 계약 기준 기대값
기대값을 구현 코드를 읽고 베끼지 않는다. 구현이 틀렸으면 테스트도 같이 틀려서 버그가 통과한다. 계약이 침묵하는 입력을 발견하면 임의로 기대값을 정하지 말고 fe-architect에게 계약 보강을 요청한다.

### 케이스 구성 — export당 최소 3종
1. **대표 경로**: 계약의 사용 예시가 그대로 동작
2. **엣지 케이스**: 빈 입력, 경계값, 유니코드, 재호출(구독 해제 후 재구독 등)
3. **에러 계약**: 계약에 명시된 throw 조건에서 실제로 명시된 에러가 발생

### 타입 레벨 테스트
공개 타입의 추론·제약은 런타임 테스트로 잡히지 않는다. 제네릭 추론 결과와 잘못된 사용의 컴파일 실패를 검증한다:
- vitest 사용 시: `expectTypeOf` (`vitest --typecheck`)
- 그 외: `// @ts-expect-error` 주석 + tsc 통과 여부

### 사이드이펙트 회귀 방지
전역 상태 금지 원칙이 지켜지는지 잡는 테스트를 둔다 — 동일 팩토리로 인스턴스 2개를 만들어 한쪽 조작이 다른 쪽에 새지 않는지 확인한다.

### 스냅샷 최소화
스냅샷은 "무엇이 옳은지"를 말하지 않아 실패 시 판단 없이 갱신하게 된다. 명시적 assertion을 우선하고, 스냅샷은 구조가 크고 안정된 출력(직렬화 포맷 등)에만 쓴다.

## 러너 관례

프로젝트에 이미 설정된 러너를 따른다. 없으면 vitest를 기본으로 하고 설치를 리더에게 보고한다. 테스트 파일은 프로젝트 기존 컨벤션(colocated `*.test.ts` 또는 `tests/`)을 따르고, 컨벤션이 없으면 colocated를 택한다.

## 리포트 형식

```markdown
# 테스트 리포트
## 커버 현황
| Export | 대표 | 엣지 | 에러 | 타입 |  (각 셀: ✅/❌/–)
## 실행 결과
{통과/실패/스킵 수, 러너 출력 요약}
## 실패 상세
| 테스트 | 원인 분류 | 전달 대상 | 상세 |
```

원인 분류는 3종: **구현 결함**(→ fe-core-builder), **계약 모호**(→ fe-architect), **테스트 오류**(→ 자체 수정). 분류 없이 "실패"만 보고하면 팀이 움직일 수 없다.
